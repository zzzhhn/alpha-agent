## 从复现到合并

1. 负责人从最新 main 新建工作树和 `codex/` 分支，先提交可确定结果的合成样例或回归测试，记录修复前的表现。
2. 修复后运行相关 pytest 或 Vitest，以及受影响的整套模块测试。前端同时运行 TypeScript、设计系统审计和构建。接口变化用项目现有命令同步 OpenAPI 和前端类型。
3. 集成人复核分支差异、测试隔离、当前 main 和共享文件。已经通过本地验收的批次及时推送并开 PR，PR 正文列出编号、验证命令和剩余验收。
4. 发布以前等 GitHub CI 和适用的预览检查通过。遇交叉改动先集成最新 main，再跑相关测试。合并后，页面验收核对登录态和实际域名；调度与账本验收另记自然运行回执。
5. 历史收益、订单和研究样本保留版本及来源。若需要迁移、回算或新研究口径，写明兼容性、成本和验收样例，按项目约定单独发布。隔离测试使用本地数据库及合成凭据。

## 盘前研究的口径决策

Opus 的补审另提出四个场景。公告窗口起点需要区分信号抓取时点与榜单实际使用的公告；未提供方向的 SEC 记录与明确的 IR 指引是否互相否决，需要对照规则验收；持有组合的增量交易成本与当前从现金建仓的独立双组合衡量不同问题；供应商短暂错误需要与真正缺失的分钟行情分开。前两种成本比较可用平价行情的小账本核对。变更冻结协议时登记版本；迟到的证据和窗口外重跑不能替代自然观察。
